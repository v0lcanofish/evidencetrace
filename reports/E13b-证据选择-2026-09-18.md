# 二、探针先量，别先改（`scripts/probe_evidence_pool.py`）

E6 的 §六 说「那 8 条的病根是**证据池只增不减、生成前无排序/剪裁**」。
动手之前先把池子的结构量出来，结果**推翻了我自己写进方案里的假设**：

| 我原来的假设 | 实测 |
|---|---|
| 「只增不减 → gold 被埋到池子后面」 | ❌ **gold 永远在池子第 0 条（8/8）** |
| 「干扰项是"多条不相关证据堆着"」 | ✅ 成立，但机制不是"堆在后面" |
| 「gold 至少和问题有点词面关系」 | ❌ **gold 与问题字面零重合（8/8，全是 0 分）** |

第三行是关键。看现场：

```
Q: How much allopurinol should I take?
gold = allopurinol 的 Dosage and Administration 节
正文: "Gout: Prior to initiating treatment assess serum uric acid level,
       complete blood count, chemistry panel, liver and kidney function tests…"
       ——**整段没有 "allopurinol" 这个词**

而被生成层挑中的干扰项是 Indications 节: "Allopurinol tablets are indicated for…"
       ——它**有**药名 → 字面重合 1 分 > gold 的 0 分 → 必然挑错
```

**⇒ 真正的病根不是"池子乱"，是"生成层手里只有一个扁平池子，
只能靠**哪个 chunk 和问题字面像**来猜该引哪条"** ——
而这条判据在**剂量类问题**上必然翻车（药名不出现在剂量正文里）。

**⇒ 而 agent 明明已经算出来了**：`coverage.py` 的 `scope`（问题点名的那份药）和
`located.loincs`（该查哪一节）—— **却一个字都没传给生成层**。
`ToolBox.answer()` 交给生成的是 `state.evidence` 的**全量原序**。

# 三、做了什么（`agent/select.py`）

**只做一件事：把 agent 在检索阶段已经算出来的结构事实，转达给生成层。**

```
检索层  决定「哪些 chunk 进池子」          —— E6 已做
选择层  决定「生成时看池子里的哪几条、什么顺序」 —— 本块
生成层  照着看到的证据写引用               —— E9
```

排序档位（**全部来自 state 字段，不读正文、不重算语义相似度**）：

```
3 = 定位章节 ∩ 焦点药   ← 结构先验说"就是这条"
2 = 定位章节            ← ⭐ E11 的跨药出处落在这档，**不许当垃圾扔**
1 = 焦点药
0 = 都不对
```

> ⚠️ **为什么不做硬剪（不按药名直接扔）**：E11 实测 `mention×absent 67` 对 ——
> 「A 的说明书提了 B，B 的说明书**没提** A」。
> **别的药的说明书有时恰恰是唯一出处**，按药名硬剪会把 E11 整块场景剪没。
> ⇒ 只做「排序 + 按预算截断」，**丢掉的理由永远只有一个：排到了预算之外**（可查）。

**没写的两处，都是刻意的**：不重算语义相似度（否则是把生成层的病抄一遍）；
不做硬剪（理由如上）。

「覆盖度说这份药没进作用域、选择层却认为有焦点药」—— **不报错**，只是排序依据悄悄变了。
本项目在闭包/归因那条路上已经因为"两套实现"栽过一次（E13 的粒度洞），这是第二次设防。

**每条被丢的都带理由**（不许静默丢弃）。

# 五、⭐ 对抗档：把池子倒过来（本块最值钱的产出）

`ET_SELECT_ORDER=reverse` 只是把池子顺序反转 —— 不改变任何一条证据的内容，只改顺序。

| | 答对率 | utilization | 拒答 | **gold 保留** |
|---|---|---|---|---|
| 正序 / K=1 | **52/60** | 8 | 8 | **60/60** |
| **倒序 / K=1** | **12/60** | **48** | 22 | **31/60** |

**⇒ 正序 K=1 的 52/60 不是"剪裁选对了"，是三个巧合叠出来的：**

```
① gold 恰好在池子第 0 条        （探针实测 8/8）
② mock 同分时取"靠前"的那条      （GroundedMockLLM._report 的 -i 排序）
③ 结构排序把 K=1 留给了它
```

池子一倒，①②同时失效，**答对率掉 40 个点**。

> **⇒ 任何"剪裁让生成层少犯错"的提升，在正序下都不可信。**
> **必须先跑一次倒序，才允许报数。**

这也解释了为什么判据 ④（反向用例：K=1 的答对率**必须**低于 K=None）**故意没过**：
**任何 K 都是 52/60** —— 这把尺子（用 GroundedMockLLM 量答对率）
**量不出证据选择的代价**。判据没过不是实现有问题，是**尺子被证明没分辨力**，
而这条必须留在判据里、不能删。

# 六、⭐⭐ 溢出发现：用这个 mock 报的**绝对数字**全军不稳

上面的倒序检验值得对**之前所有块**再做一遍。我拿它去验了 E6 的招牌结论：

| 检索器 | 池序 | 答对率 | retrieval | utilization |
|---|---|---|---|---|
| 新混合（三路+重排） | 正序 | 52/60 | 0 | **8** |
| 新混合 | 倒序 | 48/60 | 0 | **12** |
| 旧 BM25（乘性 boost） | 正序 | 52/60 | **8** | 0 |
| 旧 BM25 | 倒序 | 46/60 | **8** | 6 |

## ✅ 方向性结论是稳的

**「瓶颈搬层」在正序和倒序下都成立**：retrieval 从 8 → 0，utilization 从 0/6 往上翻。
换检索器之后病根换层，**这个结论不依赖顺序**。

## ⚠️ 但绝对数字不稳

```
utilization   8 → 12   （±50%）
答对率        52 → 48
```

**⇒ 归因的层判据是"第一个不达标的层"，而 utilization 层的判据
（`gold ⊆ cited`）恰好落进了生成层最不稳定的那块。**

**⇒ 规则（写进项目纪律）：**

> **用 GroundedMockLLM 报数时，方向性结论可以直接报；绝对数字必须附倒序对照，
> 否则不报。** 这一条比 E13b 本身值钱 —— 它保住了项目里已有的每一个绝对数字。

# 七、诚实边界

1. **收益未验证，且已知阻塞在真模型**：`代码库/.env` 的 `DEEPSEEK_API_KEY`
   **2026-09-18 复验仍是 401**（`Authentication Fails, your api key: ****0178 is invalid`），
   所以本块所有端到端数字都出自 `GroundedMockLLM`。
   **接上有效 key 之后第一件事：重扫这张 K 表 + 重跑倒序对照。**
2. **"拒答 3 → 8" 不能解读成"剪裁有害"** —— 它是 mock 判据的产物，不是系统结论。
3. **没有"定位触发但指错"的题**（E6 已记）：所以档位 2/3 的区分在本评测集上**测不出来**。
4. **档位 2（只对章节、不对药）保留下来是刻意的**，理由是 E11 的跨药出处；
   但**它在这批题上从来没被真正用上过** —— 属于机制论证，不是实测。
5. **K 没有默认打开**（`ET_EVIDENCE_BUDGET` 缺省 = 不截断）：
   实测截断在当前生成器上只有代价没有收益。**默认开着才是错的。**
   排序则默认打开（实测中性，且结构上更合理）。
