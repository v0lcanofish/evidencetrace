# EvidenceTrace · 可追溯药品问答 Agent（v3 设计）

> 2026-09-17 ｜ v1「审计层」→ v2「就是个 agent」→ **v3 补齐三块高频考点**
> **一句话**：一个在药品场景下**敢说"我不知道"**的多轮问答 agent。

---

## 0 · 设计原则（来自对 2026 面试市场的调研）

**简历项目的四大通病**（面了几十家公司的复盘原话）：
1. **功能堆砌，没有技术判断力** —"一问设计思路就卡壳：为什么选 BM25 不用稠密检索？"
2. **深度缺失，聊不出 Trade-off** —"最怕听到'我就是照着教程搭的'"
3. **场景同质化** —"智能客服、知识库问答、文档助手，面试官的耐心已经耗尽了"
4. **验证逻辑不闭环** —"写'准确率提升 15%'，细问是自己拿 20 条数据跑的，没基线"

**本设计逐条对照**：

| 通病 | 本设计的对策 |
|---|---|
| ① 功能堆砌 | 每个模块都是**场景逼出来的**，不是抄的清单（见 §1） |
| ② 深度缺失 | 在 **2 个点钻下去**：章节定位 / Verify 自查（每个都有 Trade-off） |
| ③ 场景同质化 | **药品（高风险、有 LOINC 结构）**，不是客服/文档助手 |
| ④ 验证不闭环 | **~300 条分层评测集 + 基线对比 + 消融**（见 §7） |

## 1 · 定位：它就是一个 agent

> **它的每一步都写进「证据账本」，所以它自己知道哪句话有依据。
> 没有依据的，它就不说。**

**账本是它的工作记忆，不是外挂的审计工具。** 就像人写草稿是为自己能检查。

### 和参考项目的差异（证明不是换皮）

| | 论文问答（参考） | **药品问答（我们）** | 逼出什么设计 |
|---|---|---|---|
| 答案形态 | 开放，综合多方观点 | **封闭**，说明书写着什么就是什么 | 要**精确命中某一节**，不要"多视角综合" |
| 错误代价 | 报告质量差 | **可能害人** | **拒答是核心能力** |
| 文档结构 | 自由文本 | ⭐ **SPL 结构化，章节带 LOINC 码** | ⭐ **问题类型 → 章节的机械映射** |
| 问题结构 | 单跳为主 | **多跳**（"我有胃溃疡能吃布洛芬吗"） | 必须**问题拆解** |

**⭐ 章节定位是参考项目做不了的**：
```
"能不能一起吃"  →  DRUG INTERACTIONS      "孕妇能吃吗"  →  PREGNANCY
"吃多少"       →  DOSAGE AND ADMIN       "什么副作用"  →  ADVERSE REACTIONS
```
**按结构定位，不是按语义猜。** 而且可解释："我引用了相互作用那节，因为你在问能不能一起吃。"

## 2 · 三个必须分开的概念：Context / Session / Memory

> 调研来源：harness-guide.com ——「三个词经常被混为一谈，但它们的用途完全不同」

| | 作用域 | 持久性 | 装什么 |
|---|---|---|---|
| **Context** | 单次 API 调用 | **每轮重建** | 系统提示 + 工具 + 最近消息 + 相关章节 |
| **Session** | 单次对话 | 内存中，重启丢失 | 消息历史、工具结果、当前任务状态 |
| **Memory** | **跨会话** | **写盘** | 用户偏好、已确认事实、学到的教训 |

**v2 把这三层混在一起了，v3 明确分开。**

## 3 · 架构：七阶段 + 贯穿全流程的账本

```
      ┌───────────────── 证据账本（贯穿所有阶段）─────────────────┐
      ↓            ↓            ↓           ↓          ↓        ↓
  ① Guard → ② Understand → ③ Retrieve → ④ Reflect → ⑤ Generate → ⑥ Verify
                                                                     ↓
                                                               ⑦ Memory
```

| # | 阶段 | 干什么 |
|---|---|---|
| ① | **Guard** | 范围判定：不是药品问题 → 直接拒答 |
| ② | **Understand** | 意图识别 + 指代消解 + Query 改写 + **多跳拆解** |
| ③ | **Retrieve** | ⭐ **章节定位（LOINC 映射）** + 双路召回 + RRF + 重排 |
| ④ | **Reflect** | ⭐ **证据充分性判定 + 工具失败处理** → 二次检索 / 追问 / 拒答 |
| ⑤ | **Generate** | 组织答案，每句挂**契约引用** |
| ⑥ | **Verify** | ⭐ **自查**：逐条查引用能否在账本成立，不合格**回头重写** |
| ⑦ | **Memory** | 会话记忆 + 长期记忆 + **记忆衰退** |

## 4 · 三个横切关注点（v3 新增，都是高频考点）

### 4.1 上下文预算管理

> "Context Assembly 是一个**优先级打包**问题——固定 token 预算，必须决定什么进去。"

```
┌─ Context Window（本例按 32K 规划）───────────────┐
│ ① 系统提示 + 角色约束          固定 ~600         │ ← 永不裁剪
│ ② 工具 schema（只放激活的）     固定 ~800         │
│ ③ 长期记忆摘要                 按需 ~500         │
│ ④ 本轮检索到的章节证据          ⭐ 大头，动态      │ ← 超预算时优先压缩这里
│ ⑤ 会话历史（最近 N 轮 + 摘要）  动态             │ ← 超预算时先摘要旧轮
└────────────────────────────────────────────────┘
```

**超预算时的裁剪顺序**（明确写死，不靠感觉）：
```
旧会话轮次 → 摘要
证据 chunk → 只保留与当前子问题最相关的 top-k
（永不裁剪：系统提示、当前子问题的证据）
```

**为什么这里要写清楚**：面试问"上下文超了怎么办"，答"截断"是学生答案，答"**按优先级裁剪 + 保留什么**"是工程答案。

### 4.2 ⭐ 工具调用失败处理（v2 完全缺失）

> 字节真题：**Q45 你的 Agent 如何处理工具调用失败（API 超时、返回空）？有设计重试、降级或用户澄清机制吗？**

**本项目的"工具"就是检索**，所以失败形式是：

| 失败形式 | 判定 | 应对 |
|---|---|---|
| **返回空** | 检索结果 0 条 | → 放宽 query 二次检索；仍空 → **拒答** |
| **返回不相关** | top-1 相似度 < 阈值 | → ② 重写 query 重试；重试 2 次仍低 → **追问用户澄清** |
| **超时 / 异常** | 工具抛异常 | → 指数退避重试 2 次；失败 → 降级到 BM25 单路；再失败 → 明确告知"检索不可用" |
| **结果过多** | 候选 > N | → 交给重排，只取 top-k 进上下文 |

**关键 Trade-off（面试要讲的）**：
```
重试次数 ↑  → 召回更好，但 token 和延迟 ↑
追问用户 ↑  → 体验更差（用户在问问题，不是来答题的）
拒答阈值 ↑  → 更安全，但可用性 ↓（什么都答不了）
```
**每个阈值都要有实测依据，不能拍脑袋。**（这是"通病 ④ 验证不闭环"的正面回应）

### 4.3 结构化输出约束

> 字节真题：**Q50 如何保证大模型输出稳定的 JSON？**

**每个阶段的 LLM 输出都用 schema 约束**（Pydantic）：
```
② Understand   → {"intent": ..., "sub_queries": [...], "rewritten": ...}
④ Reflect      → {"sufficient": bool, "missing": [...], "action": "retry|ask|refuse"}
⑤ Generate     → {"claims": [{"text": ..., "citations": [chunk_id...]}]}
⑥ Verify       → {"valid": bool, "invalid_citations": [...]}
```

**为什么必须约束**：下游要靠这些字段做**机械判断**（比如 Verify 要遍历 citations）。
**输出格式一崩，整条链路就断。**

## 5 · 证据账本 + 引用契约（v1 已有，v3 强化）

**三个实体**（`setid#LOINC` 串起来）：
```
Step（一步动作）──retrieved──▶ Doc（说明书章节，doc_id = setid）
                                  ▲
Claim（回答里的一条论断）──cite────┘
```

**v3 升级：引用从「字符串」变成「契约」**

> 学到的一课（开源项目 `Source-grounded RAG`）：
> **引用不该是模型临时生成的字符串，而该是摄取阶段就建立的契约。**

| 字段 | 作用 |
|---|---|
| `doc_id`（setid） | 哪份说明书 |
| `loinc` | 哪一节 |
| `chunk_id` | 哪一段 |
| `content_hash` | ⭐ **防篡改**——内容改过就露馅 |
| `char_span` | 在原文的精确位置 |
| `heading_path` | 章节路径（给人读） |

**→ 引用核验变成机械判断**：查三元组存不存在、哈希对不对。**不需要 LLM 当裁判。**

## 6 · 记忆系统（v3 加厚）

> 高频考点：Q4 短期/长期记忆设计 ｜ Q20 存储与查询优化 ｜ Q21 **记忆衰退** ｜ Q41 为什么用向量库

```
短期记忆（Session）        当前对话的消息历史 + 工作状态
    ↓ 对话结束
长期记忆（Memory）         ① 用户偏好（"我不吃阿司匹林"）
                          ② 已确认事实（"用户有胃溃疡"）
                          ③ 会话摘要
    ↓ 存储
向量库（FAISS）+ 元数据     按需检索，不是全塞进上下文
```

**记忆衰退（Q21 的答案）**：
> **旧记忆不该无限累积**——三年前的偏好未必还成立。设计：
> - 每条记忆带**时间戳 + 可信度**
> - 冲突时**新的覆盖旧的**（并记录冲突，而不是静默覆盖）
> - 超过 N 轮未被引用的记忆**降权**，不删除但检索时排序靠后

## 7 · 评测：分层评测集（v3 扩到 ~300 条）

**这是"通病 ④"的正面回应。** 参考项目有 `100+100+55+70`，我们 v2 只有 15 条。

| 评测集 | 规模 | 测什么 | 对应阶段 |
|---|---|---|---|
| **意图集** | ~100 | 意图识别 / 指代消解 / 改写 | ② |
| **章节定位集** ⭐ | ~60 | 问题类型 → LOINC 映射准不准（**我们独有**） | ③ |
| **检索集** | ~100 | Recall@5 / MRR | ③ |
| **边界集** | ~55 | 越界拒答 / 证据不足 / 多药混问 / **工具失败** | ①④ |
| **端到端集** | ~30 组多轮（120 turns） | 整条链路 + 记忆一致性 | 全部 |

### 指标

**组件级**（借参考项目方法）：
```
Intent Accuracy ｜ 章节定位准确率 ｜ Recall@5 ｜ MRR
拒答准确率 ｜ 引用准确率 ｜ Pipeline Success Rate ｜ Memory 一致性
上下文超预算率 ｜ 工具失败恢复率
```

**⭐ 跨层归因（我们的差异化）**：
```
一个答错的题，是哪一层的锅？
  ① 检索层没找到？        → 改检索
  ② 找到了但没写进答案？   → 改生成
  ③ 用了但推错了？        → 改模型
```
**测量 ≠ 诊断。** 参考项目只做组件级测量（每个零件好不好），我们额外做**整机诊断**。

### 基线对比（通病 ④ 的核心）

每个模块都要有 **before/after**：
```
只用 BM25          → Recall@5 = ?
BM25 + 稠密 + RRF  → Recall@5 = ?   ← 提升多少
+ 重排             → Recall@5 = ?
+ 章节定位         → ?              ← 我们独有的那一层贡献多少
```

## 10 · ⛔ 诚实边界（写进报告，不许含糊）

1. **`content_hash` 只能证明"这句话来自这里"，不能证明"这个推论是对的"。**
   推论合理性仍需人看。**这条必须写进报告，不能含糊。**
2. **语料只有 36 节**（6 份说明书），不是全库 —— 泛化性有限，如实写。
3. **问题是我们自己造的**（手写 + 扩题）—— 有自造偏差，不能声称"真实用户分布"。
4. **LLM 用 API** —— 换模型结果会变；但这恰好说明"**harness 决定了下限**"。
5. **不做训练** —— 本项目是 agent 系统侧；训练侧是项目一（ToolHorizon）。
