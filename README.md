## 一、定位：不做第二个 DeepResearch，做它的「审计层」

### 赛道现实（先说清楚为什么不能照做）

搜索结果里 deep research / 通用 agent 项目已经饱和：

| 项目 | Star |
|---|---:|
| Hermes Agent | 209.8k |
| Browser Use | 100k+ |
| [DeerFlow 2.0](https://www.c114.net.cn/industry/73303.html)（字节，SuperAgent 编排） | 39–81k |
| agency-agents | 87k |
| LobeHub / Chief Agent Operator | 78k |

**做"又一个 deep research 系统"，会被 DeerFlow 正面吞掉。** 参考范本本身也是这个赛道，它靠"自建 benchmark + 严格统计"才立住。

### 我们的定位

> **别人造研究 agent，我们造「判断研究为什么失败」的尺子。**

参考范本做的是：*造一个系统 → 证明它报告写得好*。
我们做的是：**审计研究过程 → 给失败归因**。

**关键：这和 ToolHorizon 是同一个研究哲学**：

| | 领域别人在做什么 | 我们在做什么 |
|---|---|---|
| **ToolHorizon** | 造 agentic RL **训练框架**（Agent Lightning / AReaL / Trinity-RFT） | 做**坍塌诊断** |
| **EvidenceTrace** | 造 deep research **系统**（DeerFlow / Hermes） | 做**过程评测 + 失败归因** |

**两个项目一句话合起来**：
> *"我这两个项目在做同一件事——**给这个领域造尺子，而不是再造一把锤子**。"*

这句话本身就是面试时最强的开场。

## 二、四个真实差异（每个都有「为什么」）

> ⚠️ **判据**：每条差异必须能在面试追问三层后仍然站得住。站不住的就是"换皮"。

### 差异 1 ｜ 评测对象：**过程** 而非 结果

| | 参考范本 | 我们 |
|---|---|---|
| 评什么 | 报告质量（事实准确率 / 幻觉率 / 引用覆盖率） | **研究过程**：证据召回率 / 证据利用率 / 检索冗余度 / 矛盾处理 |
| 为什么 | 报告是黑盒结果，**只能告诉你"不好"，不能告诉你"为什么不好"** | 过程可归因——**每一步的证据状态都能记账** |

**具体指标（我们自己定义）**：

| 指标 | 定义 | 诊断什么 |
|---|---|---|
| **证据召回率** | gold 证据集中被检索到的比例 | 检索层问题 |
| **证据利用率** | 检索到的证据里，真正进了报告的比例 | 利用层问题（找回来没用） |
| **检索冗余度** | 重复检索（同一来源/同一事实）占比 | 规划层问题 |
| **矛盾暴露率** | 遇到冲突证据时，报告是否显式处理 | 推理层问题 |
| **引用可验证率** | 报告引用的来源**是否真实存在** | 幻觉引用 |

> **这是我们最硬的差异**：别人的幻觉率是"报告里有多少错"，我们的引用可验证率是"你引的东西到底存不存在"——**后者可以机械验证，不依赖 LLM 判断**。

### 差异 2 ｜ 失败归因，而非 Red-Blue 对抗

- **参考范本**：Red Agent 攻击 → Blue Agent 修复（ADD/DELETE/MODIFY/VERIFY）
- **我们**：报告错了之后，**归因到哪一层**

**归因三层（直接迁移 ToolHorizon 的坍塌归因方法论）**：

```
报告有错
  ├─ 检索层：gold 证据根本没被找到        → 检索策略问题
  ├─ 利用层：找到了，但没进报告           → 上下文/压缩问题
  └─ 推理层：证据用上了，但结论推错       → 模型能力问题
```

**为什么这比对抗好**：
- 对抗是**打补丁**（Red 提意见，Blue 改，分数涨——但涨的原因可能是 LLM-as-Judge 的噪声）
- 归因是**找病根**，而且**三层可以用机械规则判定**，不依赖又一个 LLM 来当裁判
- 归因结果直接给出**改进方向**（检索层 → 改检索；利用层 → 改上下文；推理层 → 换模型）

### 差异 3 ｜ 证据质量分级（**我们独有**）

- **参考范本**：引用覆盖率（**数量**指标）
- **我们**：给每个来源打**质量分**，看 agent 会不会被低质证据带偏

**维度**（直接复用 `data-quality-lab` 的数据质量分级经验）：

| 维度 | 判定方式 |
|---|---|
| 权威性 | 来源类型（顶会论文 / arXiv 预印本 / 博客 / 论坛） |
| 时效性 | 发布时间 |
| 可验证性 | 是否有可核验的出处（DOI / arXiv ID / 链接可达） |
| 一致性 | 是否与其他来源矛盾 |

**新指标**：**低质证据采纳率** —— agent 引用了多少低质量来源。

> **为什么这很重要**：deep research 的真实失败模式不是"没找到"，是**"找到了不靠谱的东西还当宝贝"**。
> 这条也**直接回馈 9/18 数据岗面试的弹药包②（数据质量分级）**——一份工作两处用。

### 差异 4 ｜ 垂类做深，而非 11 领域做广

- **参考范本**：ResearchBench，11 领域 / 35 题（广而浅）
- **我们**：**一个垂类做深——AI/ML 技术调研**

**为什么选这个垂类**：

| 理由 | 说明 |
|---|---|
| 数据公开可验证 | arXiv API、OpenReview、GitHub —— 都有 ID，**引用可机械核验** |
| 有 gold 标准 | 领域内已有大量 survey，可以当"该覆盖什么"的参照 |
| 我们自己就是专家 | 用户正在做 RL/agent 方向，**能判断报告质量**（通用领域做不到） |
| **反哺项目一** | ToolHorizon 的文献调研可以直接用这个系统 |

## 三、系统设计

### 整体架构（缩减版：两块必做 + 两块选做）

```
输入：一个 AI/ML 技术问题
      ↓
┌─────────────────────────────────────────┐
│  ① 编排引擎（必做）                      │
│     plan → search → read → synthesize   │
│     每一步都往「证据账本」写一条        │
└─────────────────────────────────────────┘
      ↓
┌─────────────────────────────────────────┐
│  ③ 证据账本 Evidence Ledger（必做）      │
│     记录：每一步检索了什么 / 找到了什么   │
│           / 用了什么 / 丢了什么           │
└─────────────────────────────────────────┘
      ↓
┌─────────────────────────────────────────┐
│  ④ 过程评测 + 失败归因（必做）★核心      │
│     过程指标 → 归因三层 → 改进建议        │
└─────────────────────────────────────────┘
      ↓
  报告 + 审计报告（两个产物）
```

**选做（有时间再加）**：
- ② 证据质量分级（其实算 ④ 的一部分，量小，建议直接做）
- ⑤ 记忆压缩（简化版：只做"证据去重"，不做三级压缩）

### ① 编排引擎

**最小可行**：单 agent + 循环（plan / search / read / write），**不做多 agent**。

> **为什么不做多 agent**：多 agent 并发是参考范本最重的工程量（DAG + 信号量 + 9 状态机 + 三级降级），也是最深的水。
> 而且**它不是我们的差异点**——我们的差异在评测。**把工程量花在差异点上。**

**但要有的**：
- 每一步**埋点**（这是证据账本的输入）
- 超时 + 降级（**简化版**：单步超时跳过 + 全局超时截断）
- 确定性可复现（固定随机种子 + 固定检索顺序）

### ③ 证据账本（Evidence Ledger）

**这是整个项目的核心数据结构**，也是和其他项目最不一样的地方。

```json
{
  "step": 7,
  "action": "search",
  "query": "...",
  "retrieved": [
    {"doc_id": "arxiv:2503.14476", "title": "...", "source_type": "arxiv",
     "authority": 0.8, "recency": 0.9, "verifiable": true}
  ],
  "used_in_report": false,
  "reason_dropped": "context_budget"
}
```

**账本让我们能回答的问题**：
- 某条 gold 证据在第几步被检索到？还是从来没被检索到？
- 检索到了，为什么没进报告？（预算不够 / 被判为不相关）
- 报告里的每条引用，来自账本的第几条？

> **这就是"过程可归因"的实现**。参考范本没有这个——它的评测是对着最终报告打分。

### ④ 过程评测 + 失败归因（核心）

**评测流水线**（抄它的**统计方法**，这是标准做法，不算抄）：

```
过程指标（机械可算，不依赖 LLM）
    ↓
LLM-as-Judge（只用于"报告质量"这类确实需要判断的维度）
    ↓
Bootstrap 95% CI + Cohen's d（统计显著性）
```

**归因规则**（机械判定，这是我们的东西）：

| 现象 | 归因 | 改进建议 |
|---|---|---|
| gold 证据召回率 < 阈值 | **检索层** | 改 query 生成 / 扩召回 |
| 召回率高但利用率低 | **利用层** | 改上下文压缩 / 排序 |
| 都用上了但结论错 | **推理层** | 换模型 / 加 CoT |

**产出：一份"审计报告"** —— 不只告诉你分数，告诉你**卡在哪一层、该改什么**。

## 四、数据与评测集

### 数据集构成

| 来源 | 用途 | 现状 |
|---|---|---|
| **arXiv API** | 检索语料（AI/ML 领域） | 公开，需按需抓取 |
| **领域 survey 论文** | gold 证据集（"该覆盖什么"的参照） | 公开 |
| **HotpotQA**（深度研究变体） | 多跳推理 baseline 对照 | ⚠️ 本地**没有**，需下载 |
| **自建问题集** | 30–50 个 AI/ML 技术问题 | 自己出题（**这是真工作量**） |

**自建问题集怎么做**（这是最关键的、也最能体现"做深"的部分）：
- 每个问题配一份 **gold 证据集**（人工/半自动标注"回答这个问题必须引用哪些论文"）
- 分难度：单跳 / 多跳 / 需要综合矛盾证据
- **这是"垂类做深"的实质**——通用 benchmark 做不到这个标注粒度

### 指标总表

| 类别 | 指标 | 是否需要 LLM |
|---|---|---|
| **过程** | 证据召回率 / 利用率 / 冗余度 / 矛盾暴露率 | ❌ 机械可算 |
| **引用** | **引用可验证率**（引用是否真实存在） | ❌ 机械可算 |
| **质量** | 低质证据采纳率 | ❌ 规则可算 |
| **结果** | 事实准确率 / 覆盖度 / 连贯性 | ✅ LLM-as-Judge |
| **统计** | Bootstrap 95% CI / Cohen's d | ❌ 标准统计 |

> **设计原则**：**能机械算的都机械算**。LLM-as-Judge 只用于实在没法的维度。
> 理由：LLM 评委本身有噪声和偏见，用多了整个评测就不可信了——**参考范本的 5 维 LLM 评分恰恰是它的弱点**。

```

LLM-as-Judge 全维 → 只保留结果层 1-2 维
Bootstrap CI → 简化成置信区间估计
```

## 七、⛔ 红线

**不做（参考范本的工程量，也是我们不吹的东西）**：
- 多 agent DAG 并发拓扑 + Semaphore（工程量大、不是差异点）
- 9 状态状态机 + 三级降级策略
- Red-Blue 对抗机制（噱头 > 实质，且难验证）
- 三级语义压缩（L1 Embedding/L2 TextRank/L3 原文）→ 简化为证据去重
- 4 类 LLM 后端热切换（纯工程量，零叙事价值）
- 共享记忆的矛盾检测（启发式反义词 + 语义对立）→ 降级为"同一事实多来源标记"

**必须诚实区分**：简历/面试时说明「哪些是复用的标准方法（Bootstrap CI、LLM-as-Judge）」vs「哪些是我的设计（证据账本、三层归因、引用可验证率、低质证据采纳率）」。

**关于"换皮"的底线**：
> 相同架构换模块名 = 面试一问就穿。
> **每条差异都必须能答出"为什么这么选"**，且理由必须来自我们自己的约束/资产，而不是"我想和它不一样"。
