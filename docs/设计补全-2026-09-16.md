## 洞 1 ｜ 证据账本（Evidence Ledger）完整 schema

### 问题

README 给了一条示例 JSON，但没有：

- 账本和"报告引用"怎么对上（**这是账本能用的前提**）
- 一个 run 的完整结构
- 哪些字段是枚举化的（枚举化才能机械判定）

### 设计：三个实体 + 一条主键

账本由**三个实体**组成，它们靠 **`doc_id`（规范化的 arXiv ID）** 串起来：

```
Step（每一步动作）  ──retrieved──▶  Doc（检索到的文档）
                                     │
                                     │ doc_id 是主键
                                     ▼
Claim（报告里的每条论断）──cite──▶ Doc
```

### 1-A `Run`：一次完整研究

```json
{
  "run_id": "20260916-143022-a7f3",
  "question": "GRPO 在长链路 agent 任务上的主要失效模式是什么？",
  "model": "deepseek-chat",
  "seed": 42,
  "started_at": "2026-09-16T14:30:22",
  "steps": [ ... ],
  "claims": [ ... ],
  "report_md": "..."
}
```

### 1-B `Step`：每一步动作

```json
{
  "step": 7,
  "action": "search",
  "query": "GRPO group relative advantage variance collapse",
  "retrieved": [
    {
      "doc_id": "arxiv:2503.14476",
      "title": "...",
      "source_type": "arxiv",
      "rank": 1,
      "score": 12.3,
      "authority": 0.8,
      "recency": 0.9,
      "verifiable": true
    }
  ],
  "used_in_report": false,
  "reason_dropped": "context_budget",
  "tokens_after_step": 2345
}
```

**枚举化字段**（机械判定用，必须封闭）：

| 字段 | 取值 |
|---|---|
| `action` | `plan` \| `search` \| `read` \| `synthesize` |
| `source_type` | `arxiv` \| `openreview` \| `github` \| `blog` \| `other` |
| `reason_dropped` | `context_budget` \| `judged_irrelevant` \| `duplicate` \| `low_authority` \| `null`（= 进了报告） |

> ⭐ **`reason_dropped` 是"利用层"归因的唯一依据**。没有它，"找到了为什么没用"这个问题就只能靠 LLM 猜。

### 1-C `Claim`：报告里的每条论断

```json
{
  "claim_id": "c3",
  "text": "GRPO 的组内归一化在组内奖励全同时会退化为零梯度。",
  "cite": ["arxiv:2503.14476", "arxiv:2501.12948"],
  "first_retrieved_at_step": 7,
  "verifiable": true
}
```

**`first_retrieved_at_step` 是冗余字段，但必须存**——它是"检索层 / 利用层"归因的**直接判据**（见洞 4）。

### 1-D ⭐ 让账本"能用"的唯一要求

**报告里的每条引用，必须能解析成 `doc_id`。**

```markdown
<!-- 报告里这么写 -->
GRPO 的组内归一化在组内奖励全同时会退化为零梯度 [arxiv:2503.14476]。
```

**约束**：`synthesize` 步骤生成的报告，**引用格式必须是 `[arxiv:XXXX.XXXXX]`**，由 prompt 硬约束 + 生成后正则校验。

- 校验不通过 → 该 run 标记 `malformed`，**不进统计**
- 这是"引用可验证率"能机械算的前提（见洞 3）

### 判据

- [ ] 账本能从一次 mock run 里完整落盘成 JSON
- [ ] 给定一份报告，**能找到每一条 cite 对应的 `first_retrieved_at_step`**
- [ ] `reason_dropped` 非空的 doc，**能与"报告里没有的 doc"完全对上**

## 洞 2 ｜ 自建问题集怎么造（README 标"这是真工作量"）

### 问题

README 说要做"30–50 个 AI/ML 技术问题 + 每题一份 gold 证据集"，并承认这是手工活（风险 R3：标注太慢）。

### 设计：**反向构造，从 survey 倒推**

不要"先想问题、再找该引什么"（那是纯手工）。反过来：

```
① 选一篇 AI/ML 领域的 survey
        ↓
② 它的参考文献列表 = "回答这个领域问题必须覆盖什么" 的天然 gold
        ↓
③ 用 survey 的 section 标题 + 关键结论 生成问题
        ↓
④ gold 证据集 = 该 survey 在该 section 里引用的论文（自带 arXiv ID）
```

**为什么这个构造法是对的**：

| 好处 | 说明 |
|---|---|
| **gold 有权威来源** | 不是我们拍的，是 survey 作者的专业判断 |
| **arXiv ID 天然自带** | survey 的参考文献都有 ID → **引用可验证率可直接算** |
| **可半自动** | 解析 survey 的 LaTeX/PDF 参考文献 → 程序化生成初稿，人工只做筛选 |
| **和垂类吻合** | AI/ML 领域 survey 极多（RL/agent/多模态都有） |

### 2-A 问题模板（从 survey 结构生成）

| 模板 | 例子 | 难度 |
|---|---|---|
| `X 的核心方法有哪几类？` | "多轮 agent RL 的 credit assignment 主要有哪些做法？" | 单跳 |
| `X 和 Y 的区别是什么？` | "GRPO 和 PPO 在 advantage 估计上的区别？" | 单跳 |
| `X 为什么在 Z 场景下失效？` | "GRPO 为什么在长链路任务上容易坍塌？" | **多跳** |
| `关于 X，现有工作有哪些分歧？` | "dynamic sampling 到底有没有用，有哪些相反结论？" | **矛盾型** |

**难度分档的判据**（可执行）：

| 档 | 判据 |
|---|---|
| 单跳 | gold 证据集只有 1 篇 |
| 多跳 | gold 证据集 ≥ 2 篇，且**需要综合**才能回答 |
| 矛盾型 | gold 证据集内**存在相反结论**的论文对 |

### 2-B 每道题的产出格式

```json
{
  "qid": "q007",
  "question": "GRPO 为什么在长链路任务上容易坍塌？",
  "difficulty": "multi_hop",
  "source_survey": "arxiv:2504.xxxxx",
  "gold_evidence": [
    {"doc_id": "arxiv:2503.14476", "why_needed": "首次报告 group reward 饱和"},
    {"doc_id": "arxiv:2501.12948", "why_needed": "给出 group-relative advantage 的原始定义"}
  ],
  "notes": "survery 第 4.2 节"
}
```

### 2-C 分阶段交付（对齐 README 的降级链）

```
v1  15 题（5 单跳 + 8 多跳 + 2 矛盾）：先跑通评测，不等标注完备   ← E1 目标
v2  30 题：扩到 README 的目标量                                ← E2 目标
v3  50 题：有余力再说
```

**每一步都必须带 `gold_evidence`**——没有 gold 的题只能做"报告质量"评测，做不了"过程归因"，**等于这个项目的核心没落地**。

### 判据

- [ ] 能自动解析一篇 survey 的参考文献列表，输出 `{title, arxiv_id}` 列表
- [ ] 15 题 v1 完成，每题 gold_evidence ≥ 1 且全部有 arXiv ID
- [ ] 三档难度各至少 1 题，人工确认分档正确

## 洞 3 ｜ 引用可验证率的机械核验规则

### 问题

README 说"引用可验证率"是**最硬的差异**（"你引的东西到底存不存在"可以机械验证），但没给核验规则。

### 3-A 抽取规则

从报告 markdown 里抽三种形式的引用：

```python
PATTERNS = {
    "arxiv":  r"\[arxiv:(\d{4}\.\d{4,5})(v\d+)?\]",
    "doi":    r"\[doi:(10\.\d{4,9}/[^\s\]]+)\]",
    "url":    r"\[url:(https?://[^\s\]]+)\]",
}
```

**只认这三种，且必须带方括号标记**——正文里裸的 arXiv 编号不算引用。理由：**"它是不是有意的引用"本身要能机械判定**，不能靠猜。

### 3-B 核验规则

| 类型 | 核验方式 | 判定 |
|---|---|---|
| **arXiv** | 格式校验（`\d{4}\.\d{4,5}`，月份 `01-12`）→ 调 `http://export.arxiv.org/api/query?id_list={id}` | 返回 `<entry>` 且无 `<error>` → 存在 |
| **DOI** | `https://doi.org/{doi}` HEAD 请求 | 302/200 → 存在；404 → 不存在 |
| **URL** | HEAD 请求 | 2xx/3xx → 存在 |
| 其他 | — | **一律判为"不可核验"**，单独计数 |

### 3-C 指标定义

```
引用可验证率 = 核验通过的引用数 / 报告里引用的总条数

分母口径（必须写死，否则可操纵）：
  · 去重前：每条引用都算（同一篇引 5 次算 5 次）
  · 去重后：按 doc_id 去重（同一篇只算 1 次）
  → 两个都报，报告里标明用的是哪个
```

**为什么要两个都报**：重复引用同一篇会拉高"去重前"的分母但"去重后"不变——**两者差距本身就是"引用冗余度"的一个侧面**。

### 3-D ⚠️ 三个必须写死的实现约束

1. **必须缓存**：核验结果存 `data/citation_cache.json`，key = doc_id。同一篇论文在整个项目里只查一次。arXiv API 有 rate limit，不限速会被封。
2. **必须能离线重算**：评分脚本读缓存，**不联网也能重跑统计**。否则结果不可复现。
3. **"存在"≠"相关"**：核验只回答"这篇论文存不存在"，**不回答"它是否支持这条论断"**。
   - 后者需要 LLM 判断，**归到结果层的 LLM-as-Judge**，不要混进这个机械指标
   - **混进来 = 把这个项目最硬的差异点稀释成又一个 LLM 评委**

### 3-E 可选的加强（不改机械性）

**标题一致性粗筛**：引用存在 + 报告里给出的标题/作者与 arXiv 返回的元数据**字符串相符**。

- 完全机械（字符串比对）
- 能抓到"引了个真 ID 但写了个不相干的标题"这种幻觉
- **建议做**，成本极低

### 判据

- [ ] 给定一份含 10 条引用的 mock 报告，能正确抽出 10 条、正确定位 1 条不存在的
- [ ] 缓存命中：同一 doc_id 第二次核验**不发网络请求**
- [ ] **断网**跑评分脚本，能出完整的引用可验证率

## 洞 4 ｜ 归因三层的阈值怎么定

### 问题

README 给了归因三层的结构，但**没有阈值**。没有阈值 = 归因规则不可执行。

### 4-A 先定规则结构（阈值是后填的）

三层是**链式**的，按顺序判定，**第一个不达标的层就是病根**：

```
对一道错题：
  ① 检索层达标吗？（gold 证据被找到了吗）
       否 → 归因「检索层」，停
       是 ↓
  ② 利用层达标吗？（找到了的，进报告了吗）
       否 → 归因「利用层」，停
       是 ↓
  ③ 推理层：证据都进了报告还是答错 → 归因「推理层」
```

**为什么必须是链式而不是并列**：后一层依赖前一层。检索层没达标时谈"利用率低"没有意义——**没找到的东西谈不上没利用**。

### 4-B 三个指标的操作性定义（这部分是硬的，可以直接写死）

| 层 | 指标 | 计算 |
|---|---|---|
| **检索层** | `证据召回率` | `|{gold_doc_id} ∩ {所有 step 的 retrieved doc_id}| / |{gold_doc_id}|` |
| **利用层** | `证据利用率` | `|{gold_doc_id} ∩ {claims 里 cite 的 doc_id}| / |{gold_doc_id} ∩ {retrieved doc_id}|` |
| **推理层** | `引用存在性正确率` | 该题的错是否发生在"证据齐全但结论错"——需要 LLM-as-Judge 判 claim 与 cite 是否矛盾 |

⭐ **注意利用层的分母是"召回了的 gold"，不是"全部 gold"**——这正是链式归因的体现。

### 4-C ⚠️ 阈值**不能现在拍**，必须先跑 baseline 校准

**这是本节最重要的一条。**

如果现在写"召回率 < 0.5 → 检索层问题"，那是**拍脑袋**。正确做法：

```
① 先跑 baseline（单 agent + BM25/arXiv 检索，不做任何调优）
② 得到 15 题的三个指标分布
③ 阈值取「baseline 分布的某个分位」：
     检索层阈值 = baseline 召回率的 p25
     利用层阈值 = baseline 利用率的 p25
④ 把 baseline 的数字和阈值一起写进文档，注明「阈值由 baseline 校准而来」
```

**为什么必须这样**：

- 拍脑袋的阈值 = **用结果倒推标准** = 论文里最容易被审稿人打死的地方
- 先跑 baseline 再定阈值 = **标准的诊断学做法**（先有正常值范围，再有异常判定）
- 而且 baseline 的数字本身就是**第一个交付物**——它告诉你这个 agent 现在卡在哪一层

### 4-D 归因结果长什么样

```json
{
  "qid": "q007",
  "run_id": "20260916-143022-a7f3",
  "correct": false,
  "metrics": {"recall": 0.33, "utilization": null},
  "attribution": "retrieval",
  "evidence": "gold 3 篇，只召回了 1 篇：缺 arxiv:2503.14476, arxiv:2501.12948",
  "suggestion": "query 生成没有覆盖 'credit assignment' 这一支"
}
```

**`suggestion` 字段是审计报告的价值**——不只告诉你分数，告诉你**该改哪**。

### 判据

- [ ] baseline 跑完 15 题，三个指标分布出表
- [ ] 阈值由 baseline p25 算出，**数字和来源都写进文档**
- [ ] 给定一道错题，归因脚本能输出上面那个 JSON

## 洞 5 ｜ 编排引擎接口（mock 跑通的形态）

### 问题

README 给了架构图，没给接口。E0 里程碑的出口是"端到端跑出第一份报告"，需要一个明确的 mock 形态。

### 5-A 接口（最小）

```python
class ResearchAgent:
    def __init__(self, llm, retriever, ledger, max_steps=20):
        ...

    def plan(self, question: str) -> list[str]:
        """生成子问题。每步写一条 action='plan' 的账本记录。"""

    def search(self, query: str) -> list[Doc]:
        """检索。返回的每篇都记进账本的 retrieved 字段。"""

    def read(self, doc: Doc) -> str:
        """读全文 / 摘要。"""

    def synthesize(self, question: str, evidence: list[Doc]) -> str:
        """生成报告。引用格式硬约束为 [arxiv:XXXX.XXXXX]。"""

    def run(self, question: str) -> Run:
        """主循环：plan → (search → read)* → synthesize"""
```

**三个必须有的**（README 已列，这里补实现形态）：

| 要求 | 做法 |
|---|---|
| **每步埋点** | `ledger.record(step)` 是**唯一的写账本入口**，不允许绕过 |
| **确定性可复现** | `seed` 固定 + **检索顺序固定**（不用 set / dict 遍历顺序）+ 时间戳只在 run 级别产生 |
| **超时降级** | 单步超时 → 跳过并记 `reason_dropped="timeout"`；全局超时 → 截断并标记 run `truncated` |

### 5-B mock 形态（E0 出口判据）

```python
# mock 三件套
class MockRetriever:
    """从本地 JSON 里返回固定文档，不发网络请求"""
    def search(self, query, k=5): ...

class MockLLM:
    """按脚本返回固定文本：第一轮给子问题，第二轮给报告"""
    def __call__(self, prompt): ...

# 判据
def test_end_to_end():
    run = ResearchAgent(MockLLM(), MockRetriever(), Ledger()).run("测试问题")
    assert run.report_md                          # 产出报告
    assert len(run.steps) > 0                     # 有账本
    assert all(c.cite for c in run.claims)        # 每条 claim 有引用
    assert 每个 cite 都能在 steps 里找到 doc_id     # ★ 闭包检查
```

**最后一条断言是核心**：**账本和报告必须闭合**——每条引用都能追到某一步的检索。这一条过了，项目的核心机制就成立了。

### 5-C 与 README 架构图的对应

```
① 编排引擎（必做）        → ResearchAgent + 两个 mock
③ 证据账本（必做）        → Ledger（洞 1 的 schema）
④ 过程评测 + 失败归因     → 洞 3 的核验 + 洞 4 的归因
```

**顺序建议**：**先做 ③ 和 ④，再做 ①**。
理由见 README 风险 R4——"如果只做编排不做评测，就变成又一个 RAG 玩具"。**先把尺子造出来，再让 agent 跑。**

### 判据

- [ ] `python run.py --mock` 端到端跑通，输出 `report.md` + `audit.json`
- [ ] 账本-报告闭包断言通过
- [ ] **断网**能跑（mock 不碰网络）
- [ ] 同一 seed 跑两次，账本 JSON **完全一致**（确定性）

## ⛔ 本次补全新增的红线

在本文件的设计过程中，有三处特别容易滑向"看起来专业但没意义"：

1. **"存在"≠"相关"**：引用可验证率只回答"这篇论文存不存在"。**不要把"是否支持论断"混进来**——那需要 LLM 判断，会把这个项目最硬的机械指标稀释成又一个 LLM 评分。
2. **阈值不能拍**：归因三层的阈值**必须先跑 baseline 再定**，且数字和来源一起写进文档。拍脑袋的阈值 = 用结果倒推标准。
3. **先造尺子再造锤子**：编排引擎是脚手架，**评测和归因才是主线**。E0 之前先把洞 1 的 schema 定死。
