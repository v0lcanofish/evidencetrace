## 🔴 场景变更说明（2026-09-16 · E-4 探针后）

**原定"中文药品说明书（NMPA）"方案作废** —— NMPA 主站与数据共享平台实测 **HTTP 412（WAF/JS challenge）**，
加完整浏览器请求头同样 412，**不可用于研究语料**。

**改用 DailyMed（美国国家医学图书馆）**：

| | NMPA（作废） | **DailyMed（采用）** |
|---|---|---|
| 可达性 | ❌ HTTP 412 | ✅ **公开 API，免认证** |
| 唯一 ID | 批准文号 | **`setid`（UUID）** |
| 章节结构 | 文本标题【禁忌】 | ⭐ **LOINC 编码（机械可判）** |
| 批量 | 难 | ✅ 有分页 |

> ⭐ **LOINC 章节码是关键升级**：它意味着「回答这个问题**该引哪一节**」是**机械可判**的，
> gold 证据集可以**半自动构造**——这比中文说明书的文本标题强得多。

**代价（诚实记录）**：语言从中文变英文，少了"中文语料 / 中文分词"这个亮点；
业务感需要靠"**跨境医药电商 / 出海药企**"来锚定。详见 `reports/E4-数据源探针-2026-09-16.md`。

## 🔄 v2 升格说明（2026-09-16）

### 为什么升格

v1 的定位是"只做审计层"，**在简历上会被读成"只做了分析，没造出东西"**。
对照一份 RL + Agent 双线简历（Agent 那条是"造系统 + 5 套评测集"），必须补齐**系统形态**。

### 升格了什么 / 保留了什么

| | v1 | **v2** |
|---|---|---|
| 编排 | 4 阶段（plan-search-read-synthesize） | **7 阶段** |
| 语料 | arXiv 单源 | **药品说明书 + 章节感知分块** |
| 检索 | 只用 BM25 | **中文 BM25 + 稠密 + RRF + 重排** |
| 工程 | 无 | **AgentState + 两级 PipelineTrace + CLI** |
| 评测集 | 30 题 | **4 套**（对话集 / 意图 / 检索标注 / 边界） |
| **核心差异** | 账本 + 三层归因 + 引用可验证率 | ✅ **原样保留** |

> ⚠️ **右下角那行不能动。** 升格加的是"系统形态"，不是替换差异点——
> 否则就是市场上那一堆 RAG 玩具的低配版（nano-cc / DeerFlow / Hermes 已经饱和）。

## 一、定位：两个身份，一个内核

### 身份 1（业务面）：跨境医药电商的多轮药品信息问答 Agent

**场景**：出海药企 / 跨境医药电商的用药咨询，用户问——
> "I'm on blood pressure medication — can I take this ibuprofen together?"
> "I'm three months pregnant, can I take this drug?"

**语料**：**FDA 药品说明书**（DailyMed，美国国家医学图书馆公开库）

**业务痛点**：
- **答错有医疗 + 法律双重风险**——FDA 说明书是法定文件，答错要担责
- 跨境场景下**没有本土药师**可问，agent 是唯一入口
- 药品信息必须**可溯源到说明书原文**，不能凭空生成

### 身份 2（研究面）：给 agent 造尺子

> **别人造的用药咨询 agent 只能告诉你"答得不好"，我造的能告诉你"卡在哪一层、该改什么"。**

**和项目一是同一个研究哲学**：

| | 领域别人在做什么 | 我们在做什么 |
|---|---|---|
| **ToolHorizon** | 造 agentic RL **训练框架** | 做**坍塌诊断** |
| **EvidenceTrace** | 造用药咨询 **问答系统** | 做**过程评测 + 失败归因** |

**两个项目一句话合起来**：
> *"我这两个项目在做同一件事——**给这个领域造尺子，而不是再造一把锤子**。"*

## 二、⭐ 核心差异：为什么"引用可验证率"在这里是生死攸关的

在这个场景里，agent 说的每一条用药建议**都必须能追溯到说明书原文**。

**要回答的那个具体问题**：
> **"它引的那条【药物相互作用】，说明书里到底有没有？"**

这不是学术指标，是**能不能上线的前提**。而且它**可以机械核验**——药品批准文号（国药准字）是唯一 ID，说明书章节是固定结构。

### 四项能力（机械可算，不依赖 LLM 裁判）

| 能力 | 定义 | 诊断什么 |
|---|---|---|
| **证据召回率** | gold 说明书章节被检索到的比例 | 检索层问题 |
| **证据利用率** | 检索到的章节里真正进了回答的比例 | 利用层问题 |
| **三层归因** | 检索层 / 利用层 / 推理层 | **卡在哪一层、该改什么** |
| **引用可验证率** | 回答引用的**批准文号与说明书章节**是否真实存在 | 幻觉引用 |

> **设计原则：能机械算的都机械算。** LLM-as-Judge 只用于"回答质量"这类实在没法的维度。
> 理由：LLM 评委自身有噪声和偏见，用多了整个评测就不可信了。

## 三、系统设计

### 3.1 七阶段编排

```
输入：一条多轮用药咨询
      ↓
① Guardrails    → 越界检测（问诊断/处方 → 直接拒答）
② NLU           → 意图识别 + 药品实体归一 + 指代消解 + Query 改写
③ Retrieve      → 中文 BM25（稀疏） + BGE-M3（稠密）
④ Rerank        → RRF 融合 → Cross-Encoder 重排
⑤ Reflect       → 证据充分吗？不足 → 二次检索 或 主动拒答
⑥ Synthesize    → 生成回答，引用格式硬约束
⑦ Audit         → 写审计报告（归因 + 改进建议）
      ↓
产出：回答 + 审计报告（两个产物）

   每一步都往【证据账本】写一条 ────────────┘
```

**⑥ 的硬约束**：回答里的引用格式必须是 `[国药准字XXXXXXXX]`，由 prompt 约束 + 生成后正则校验。
**校验不过 → 该 run 标记 `malformed`，不进统计。**

### 3.2 证据账本（Evidence Ledger）—— 核心数据结构

三个实体靠 **`doc_id`（药品批准文号）** 串起来：

```
Step（每一步动作） ──retrieved──▶ Doc（说明书章节）
                                   │ doc_id 主键
                                   ▼
Claim（回答里的每条建议）──cite──▶ Doc
```

```json
{
  "step": 7,
  "action": "retrieve",
  "query": "布洛芬 降压药 相互作用",
  "retrieved": [{
    "doc_id": "国药准字H20033974",
    "section": "药物相互作用",
    "text": "...",
    "rank": 1, "score": 12.3,
    "authority": 0.9, "recency": 0.8, "verifiable": true
  }],
  "used_in_report": false,
  "reason_dropped": "context_budget"      // ← 枚举化，利用层归因的唯一依据
}
```

**枚举化字段**（必须封闭，否则无法机械判定）：
- `action`: `plan` | `retrieve` | `read` | `synthesize`
- `reason_dropped`: `context_budget` | `judged_irrelevant` | `duplicate` | `low_authority` | `null`

**`first_retrieved_at_step`** 是冗余字段但必须存——它是检索层/利用层归因的**直接判据**。

### 3.3 三层归因（链式，不是并列）

```
对一条错误回答：
  ① 检索层达标吗？（gold 章节被找到了吗）
       否 → 归因「检索层」，停
       是 ↓
  ② 利用层达标吗？（找到了的进回答了吗）
       否 → 归因「利用层」，停
       是 ↓
  ③ 推理层：证据齐了还是答错 → 归因「推理层」
```

**为什么必须链式**：后一层依赖前一层——**没找到的东西谈不上没利用**。

⚠️ **阈值必须由 baseline 校准（取 p25），不能拍脑袋。** 拍脑袋的阈值 = 用结果倒推标准。

### 3.4 工程深度

- **AgentState 扩展** + **Turn / Stage 两级 PipelineTrace**：记录各阶段输入输出、工具调用、耗时、证据状态
- **CLI**：`/trace`（看某条回答的完整链路）、`/corpus`（查语料）、`/audit`（看审计报告）
- **确定性可复现**：固定 seed + 固定检索顺序（不用 set/dict 遍历序）+ 时间戳只在 run 级别产生

## 四、数据与评测集

### 4.1 语料

| 项 | 内容 |
|---|---|
| 来源 | ✅ **DailyMed（美国 NLM）** —— `/services/v2/spls.json` + `/spls/{setid}.xml`，公开 API、有分页 |
| 格式 | **HL7 SPL XML**（法定结构化格式） |
| 分块 | ⭐ **章节感知分块**——按 LOINC 章节码切（Indications / Contraindications / Drug Interactions / Dosage…） |
| 元信息 | **`setid`**（唯一 ID）、药品名、剂型、厂家、版本日期、**LOINC 章节码** |

> ⭐ **LOINC 章节码是本项目的关键资产**：「该引哪一节」**机械可判** → gold 证据集半自动构造。
> SPL 的章节结构由 HL7 标准约束，比自由文本的说明书标题稳定得多。

### 4.2 四套评测集

| 集 | 规模 | 覆盖什么 |
|---|---|---|
| **多轮对话集** | 30 组四轮（120 turns） | 指代消解、二次检索、跨药比较 |
| **意图集** | 100 条 | 意图识别 + 药品实体归一的分类准确率 |
| **检索标注集** | 100 条 | 每题标 gold 章节 |
| **边界集** | 55 条 | 超说明书用药 / 孕妇儿童禁忌 / 越界拒答 |

### 4.3 指标总表

| 类别 | 指标 | 需要 LLM 吗 |
|---|---|---|
| **引用** | **引用可验证率**（批准文号 + 章节是否存在） | ❌ 机械 |
| **过程** | 证据召回率 / 利用率 / 检索冗余度 | ❌ 机械 |
| **归因** | 三层归因分布 | ❌ 机械（规则判定） |
| **质量** | 低质证据采纳率（四维分级） | ❌ 规则 |
| **组件** | 意图五分类 / 实体归一 / Recall@5 / 拒答准确率 / Pipeline Success Rate | 部分 |
| **结果** | 回答事实准确率 / 覆盖度 | ✅ LLM-as-Judge |
| **统计** | Bootstrap 95% CI / McNemar 精确检验 | ❌ 标准统计 |

## 八、⛔ 红线

**不做（参考范本的工程量，也是不吹的东西）**：
- 多 agent DAG 并发拓扑 + Semaphore
- 9 状态状态机 + 三级降级策略
- Red-Blue 对抗机制
- 三级语义压缩 → 简化为证据去重
- 4 类 LLM 后端热切换

**三条设计红线**：
1. ⭐ **"存在" ≠ "相关"** —— 引用可验证率**只回答"这条引用存不存在"**，绝不混"是否支持该论断"（后者需要 LLM，会把这个最硬的机械指标稀释掉）
2. **阈值不能拍** —— 必须先跑 baseline 再校准
3. **先造尺子再造锤子** —— 先做账本和归因，再做编排

**必须诚实区分**：`Bootstrap CI / LLM-as-Judge / BGE-M3 / RRF / Cross-Encoder` 是**标准方法**；
`证据账本 / 三层归因 / 引用可验证率 / 低质证据采纳率` 是**我们的设计**。
