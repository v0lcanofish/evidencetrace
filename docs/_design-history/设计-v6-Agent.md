# EvidenceTrace · 设计 v6 —— **它是 agent，不是 RAG**

> 2026-09-17 ｜ v5 是「七阶段线性流水线」= **本质上是 RAG**，作废。
> v6 改成 **agent loop**：LLM 自主决定下一步，工具集可选，状态可查，结果有反馈。

---

## 0 · 一句话

> **一个药品咨询 agent。它自己决定下一步做什么——查哪一节、要不要再查、
> 要不要问用户、什么时候该作答、什么时候该说"我不知道"。**
>
> **而它的每一个决定都要过机械检查：引用能不能追溯到真实存在的证据块。**

---

## 1 · 为什么 v5 不算 agent

| | v5（七阶段流水线） | **v6（agent loop）** |
|---|---|---|
| 控制流 | **写死的顺序**：Guard→Understand→Retrieve→... | **LLM 每轮自己决定下一步** |
| 循环 | ❌ 只有 ④ 一个决策点，走一次 | ✅ 想查几次查几次，随时可以回头 |
| 工具 | 只有"检索" | ✅ 定位 / 检索 / 追问 / 作答 / 拒答 |
| 状态 | 无 | ✅ 已知什么、还缺什么、试过什么 |
| 反馈 | 无 | ✅ 机械检查结果**反过来影响下一步决策** |

**一句话**：v5 是"**流程**"，v6 是"**循环**"。

---

## 2 · 架构：Agent Loop

```
┌───────────────────────────────────────────────────────────────┐
│                      Agent Loop                                │
│                                                                │
│   状态 s = {                                                 │
│     问题, 已确认事实, 还缺什么, 试过哪些查询, 剩余预算         │
│   }                                                            │
│        ↓                                                       │
│   ⭐ LLM 决策：下一步做什么？（结构化输出）                     │
│        ↓                                                       │
│   ┌──────────────────────────────────────┐                     │
│   │  工具集（agent 自选，可多次调用）      │                     │
│   │                                       │                     │
│   │  locate_section(drug, intent)         │ ← 定位到该查哪节   │
│   │  search(query, section=None)          │ ← 检索             │
│   │  ask_user(question)                   │ ← 问用户澄清       │
│   │  answer(claims)                       │ ← 作答（带引用）    │
│   │  abstain(reason)                      │ ← 拒答             │
│   └──────────────────────────────────────┘                     │
│        ↓                                                       │
│   ⭐ 机械检查（账本，不问 LLM）                                 │
│      · 引用的 chunk 在索引里吗？content_hash 对得上吗？         │
│      · 证据对 claim 的覆盖够不够？（算出来的，不是模型感觉）     │
│        ↓                                                       │
│   把检查结果**反馈回状态** → 下一轮                             │
│        ↓                                                       │
│   直到 agent 调 answer() 或 abstain()，或撞预算上限             │
└───────────────────────────────────────────────────────────────┘
```

**三个东西让它成为 agent**：
1. **LLM 主导控制流** —— 不是写死的顺序，是模型每轮自己选
2. **工具集** —— 五种工具，agent 自己挑、自己决定调几次
3. **机械反馈闭环** —— 检查结果反过来改变 agent 下一步的行为

## 3 · ⭐ 核心研究问题：**行动决策边界**

> **agent 什么时候该停止行动？**

```
太早停  →  证据不够就答  →  幻觉
太晚停  →  无限查下去    →  成本爆炸、延迟不可接受
```

这是 agent 领域的**开放问题**。现有做法：
```
Self-RAG        → 反思 token（靠模型学）
迭代 RAG         → 固定轮数（拍脑袋）
ReAct           → 靠模型自觉
```

**我们的角度**：
> **停止准则不靠模型自省，靠【账本的证据覆盖度】算。**
> 每一轮检查：当前证据能不能撑起一个完整答案？
> 撑不起 → 继续（并给出"还缺什么"）；撑得起 → 停。

---

## 4 · ⭐⭐ 和项目一是同一个问题的两面

```
🅰️ 项目一（训练侧）  agent 什么时候该【调用工具】？
     欠调用 = 该动不动 ｜ 过调用 = 不该动乱动 ｜ 抖动 = 反复横跳

🅱️ 项目二（推理侧）  agent 什么时候该【停止行动】？
     查不够 = 证据不足就答 ｜ 查太多 = 浪费 ｜ 该问不问 = 瞎猜
```

**两个项目在问同一件事：agent 的行动决策边界。**

这么讲：
> "我两个项目在研究同一个问题——**agent 什么时候该采取行动**。
> 项目一在**训练侧**看这个能力会不会退化；项目二在**推理侧**做停止准则。"

**这样两个项目是一体的，不是"一个 RL 一个 RAG"。**

## 5 · 工具集（这是 agent 的"手"）

| 工具 | 输入 | 输出 | 谁来决定调用 |
|---|---|---|---|
| `locate_section` | drug, intent | LOINC 码 | **LLM**（v5 是写死的） |
| `search` | query, section? | [Chunk] | **LLM**（可换 query 重查） |
| `ask_user` | question | 用户回复 | **LLM**（信息不够时） |
| `answer` | claims[] + citations[] | — | **LLM**（但引用要过核验） |
| `abstain` | reason | — | **LLM**（但证据覆盖度也算了） |

**关键**：调哪个、调几次、按什么顺序 —— **全由 agent 决定**。

## 6 · 机械检查（这是"可验证"的来源）

**每轮都跑，结果反馈给 agent：**

```python
def check(state):
    report = {
        # ① 引用核验（事实判断，不问 LLM）
        "invalid_citations": [c for c in state.citations
                              if not verify_chunk(c, index)],
        # ② 证据覆盖度（算出来的）
        "coverage": compute_coverage(state.claims, state.evidence),
        # ③ 缺失信息（告诉 agent 还缺什么）
        "missing": find_missing(state.question, state.evidence),
    }
    return report
```

⚠️ **`verify_chunk` 是机械的**：查 chunk_id 在不在索引 + content_hash 对不对。
   这是"引用契约"的落地 —— **出处真实性 = 事实判断，不是语义判断**。

## 7 · 和前沿的对话

| 工作 | 关系 |
|---|---|
| **VeriCite** (SIGIR-AP 2025) | 它用 **NLI 模型**验证 claim-entailment；我们用**契约**验证出处真实性 —— **互补** |
| **AbstentionBench** (2026) | "拒答是 trivially faithful，拒错了指标看不见" → 我们用**证据覆盖度**做拒答判据 |
| **arXiv 2606.04990** | provenance 综述，我们的账本对齐它的框架 |
| **Self-RAG / 迭代 RAG** | 它们的停止准则是**学的**或**固定轮数**的；我们是**算的** |

## 8 · 实验设计

### 实验 1 · 停止准则对照 ⭐

```
配置 A  固定轮数（迭代 RAG 的常见做法）
配置 B  LLM 自评"够不够了"
配置 C  账本覆盖度判定          ← 我们的
配置 D  B + C

指标：答案准确率 ｜ 平均检索轮数 ｜ ★过度检索率 ｜ 漏检率 ｜ 拒答准确率
```

### 实验 2 · 引用验证对照

```
配置 A  无验证
配置 B  NLI 验证（复现 VeriCite）
配置 C  契约核验        ← 我们的
配置 D  B + C

指标：引用准确率 ｜ 拒答准确率 ｜ 过度拒答率
```

### 实验 3 · 跨层归因

```
答错的题，看账本判断是哪一层的锅：
  检索层（没找到）｜ 利用层（找到没用）｜ 决策层（该继续查却停了）
```

## 12 · 诚实边界

1. 概念框架参考 arXiv 2606.04990 / VeriCite / AbstentionBench，**不是我们首创**
2. `content_hash` 只证明"出处真实"，**不证明"推论正确"**
3. 语料 50 份药，非全库
4. 问题自造，有偏差
5. LLM 用 API
