# EvidenceTrace · 详细设计 v4

> 2026-09-17 ｜ v3 的问题：**堆了太多东西**。
> v4 的原则：**每个模块都必须回答"不做会怎样"**，答不上来的就砍掉。

---

## 0 · 一句话

> **一个在药品场景下敢说「我不知道」的可追溯问答 agent。**
> 它的每一句话都能追到说明书的具体某一节；追不到，它就不说。

---

## 1 · 三个差异化（其余都是常规工程）

| # | 差异化 | 一句话 | 别人做不了的原因 |
|---|---|---|---|
| **①** | **章节定位** | 问题 → 直接定位到该查哪一节（LOINC） | 论文/网页是自由文本，**没有结构可定位** |
| **②** | **拒答是核心能力** | 证据不够就说不知道 | 一般 RAG 倾向于"编一个看起来合理的" |
| **③** | **跨层归因** | 答错了，能指出是检索层/利用层/推理层的锅 | 组件级指标只能告诉你"零件好不好"，不能诊断 |

**⚠️ 不做的事**：多智能体对抗、DAG 编排、知识图谱、上下文三级压缩、多后端热切换。
理由见 §6。

---

## 2 · 架构：七阶段（线性，不是 DAG）

```
   用户问题
      ↓
   ┌──────────────────── 证据账本（贯穿，每步都写）────────────────────┐
   ↓          ↓           ↓           ↓           ↓          ↓
 ①Guard → ②Understand → ③Retrieve → ④Reflect → ⑤Generate → ⑥Verify
                                                                  ↓
                                                            ⑦Memory
```

### 每阶段的契约（输入 → 输出 → 判据）

| # | 阶段 | 输入 | 输出（结构化） | **判据** |
|---|---|---|---|---|
| **①** | Guard | 问题 + 会话状态 | `{in_scope, reason}` | 边界集 `out_of_scope` **全拦下** |
| **②** | Understand | 问题 + 会话历史 | `{intent, drug, sub_queries[], resolved_query}` | 端到端集**指代消解全对** |
| **③** | Retrieve | `sub_queries` | `[Chunk]`（带 rank/score） | 检索集 **Recall@5 / MRR** |
| **④** | Reflect | 检索结果 | `{sufficient, action, missing[]}` | 边界集 `refuse_*` **全拒** |
| **⑤** | Generate | 证据 chunks | `{claims:[{text, citations[]}]}` | 引用格式**合法率 100%** |
| **⑥** | Verify | claims | `{valid, invalid[]}` | 注入坏引用**必被抓住** |
| **⑦** | Memory | 本轮 turns | 更新后的会话状态 | 端到端集**多轮一致** |

> **每个阶段都用结构化输出约束**（Pydantic / JSON schema）。
> 因为下游要靠这些字段做**机械判断**——格式一崩整条链路就断。

## 3 · 数据结构：证据账本 + 引用契约

### 三个实体

```
Step（一步动作）──retrieved──▶ Chunk（说明书片段）
                                │ chunk_id = {setid}#{loinc}#{序号}
                                ▼
Claim（回答里的一条论断）──cite──▶ Chunk
```

### 引用契约（**索引建立时就定好，不是模型现编的**）

| 字段 | 作用 |
|---|---|
| `chunk_id` | 唯一标识（`setid#loinc#n`） |
| `doc_id` | 哪份说明书（setid） |
| `loinc` | 哪一节 |
| `char_span` | 在原文的**精确位置** |
| `heading_path` | 章节路径（给人读） |
| `content_hash` | ⭐ **防篡改** —— 内容改过就露馅 |

### 核验 = 机械判断

```
查 chunk_id 在不在索引里  →  查 content_hash 对不对得上
```

**不问 LLM。** 这是"可追溯"和"让 GPT 打分"的本质区别。

### 归因判据（差异化 ③）

```
一个答错的题，看账本就知道是哪层：
  检索层   —— 该引的 chunk 压根没进 top-k        → 改检索
  利用层   —— 进了 top-k 但没写进 claims          → 改生成
  推理层   —— 写进 claims 了，但结论错            → 改模型（或标注 gold 错）
```

**这三条全从账本推导，不需要人看答案。**

### v4 评测集

| 集 | 条数 | 测什么 | 对应判据 |
|---|---|---|---|
| `retrieval` | ~60 | 检索召回（direct / paraphrase 两档） | ③ |

### 指标

```
Recall@5 ｜ MRR            ← 检索
定位准确率                  ← 章节定位
拒答准确率                  ← 边界（分类：该拒/该答）
引用准确率                  ← 核验通过率
Pipeline Success Rate      ← 端到端跑通
⭐ 跨层归因分布             ← 失败题目里，各层各占多少
```

## 6 · ⛔ 不做什么（这一节最重要）

**判断标准：不做会怎样？答不上来的，就不做。**

| 不做 | 为什么 |
|---|---|
| **多智能体 / Red-Blue 对抗** | 我们的错误来源是"证据不够"，不是"观点冲突"。对抗解决不了拒答问题 |
| **DAG 编排** | 七阶段是**线性**的，没有并行分支。加 DAG 是过度设计 |
| **知识图谱 / GraphRAG** | 药品说明书是**扁平的章节结构**，没有实体关系需要图 |
| **上下文三级压缩** | 我们的对话最长 4 轮，**根本不会撑爆上下文**。压缩是无用功 |
| **多后端热切换** | 只需要 1 个 LLM（DeepSeek）。换后端是演示需求，不是研究需求 |
| **通用深度研究** | 那是参考项目的场景。我们做药品，**答案封闭、可机械判定** |
| **训自己的 LLM** | 项目一已经覆盖训练侧。项目二的定位是**系统侧** |

### 可选的加码（做完主线再决定）

```
① 扩语料（6 份药 → 100 份）—— 提升评测泛化性
② 微调检索器（BGE-M3）—— 唯一的 GPU 用武之地，天然有"从 X 到 Y"
```

**这两个都是"扩"，不是"补缺"。主线做完才考虑。**

## 7 · ⛔ 诚实边界（写进报告，不许含糊）

1. **`content_hash` 只能证明"这句话来自这里"，不能证明"这个推论是对的"**
2. 语料只有 **36 节（6 份药）**，泛化性有限
3. 问题是我们自己造的（手写 + 模板扩），**有自造偏差**
4. LLM 用 API，换模型结果会变
5. **不做训练**（系统侧项目）—— 训练侧是项目一
